# merged-index-p: Part–Partsupp–Lineitem index

This standalone library supplies the concrete MI_P definition for DBSP's general merged-index module, `dbsp::trace::merged_index`. It holds steps 1 and 2 of [new-merged-index.md](../../../docs/design/merged-index/new-merged-index.md): the spec, its generated module, tests that pin the encoding, and storage tests with file runs. It has no readers, view circuit, or harness yet. Shared rules for any index and harness are in [experiments/CLAUDE.md](../CLAUDE.md); the generic machinery is in [crates/dbsp/src/trace/merged_index/CLAUDE.md](../../../crates/dbsp/src/trace/merged_index/CLAUDE.md). The sibling [merged-index-col](../merged-index-col/CLAUDE.md) is the worked example.

## Definition

The definition is generated by the SQL compiler from `mi_p.mi` and `schema.sql` into the committed `src/generated.rs`, which the crate root re-exports. `lib.rs` adds only `build_batch` (DBSP's default filters) and `build_batch_in` (given factories, such as `batch::index_factories::<StoredPayload>(&TRIE)`, whose files get a prefix filter over the part group). Regenerate with `generate.sh` (rule in [experiments/CLAUDE.md](../CLAUDE.md)); do not edit `generated.rs` by hand.

`schema.sql` holds each table's primary key, the trie's key columns, and the payload columns, plus Q14's predicate-free join `V = Part ⋈ Lineitem` on `partkey`. The payloads serve Q14 only (user decision of 2026-11-19); a later query adds its columns to `schema.sql` and `mi_p.mi`, then regenerates.

Folded keys are 11, 20, and 34 bytes:

```text
domain tags:    INDEX = 0x00, partkey = 0x01, suppkey = 0x02, orderkey = 0x03, linenumber = 0x04
placement ids:  PartByPartkey = 0x01, PartsuppByPartkeySuppkey = 0x02,
                LineitemByPartkeySuppkeyOrderkeyLinenumber = 0x03

P(p):          0x01 fold_i64(p) | INDEX | 0x01                                                  (11 bytes)
PS(p,s):       0x01 fold_i64(p) | 0x02 fold_i64(s) | INDEX | 0x02                               (20 bytes)
L(p,s,o,l):    0x01 fold_i64(p) | 0x02 fold_i64(s) | 0x03 fold_i64(o) | 0x04 fold_i32(l) | INDEX | 0x03   (34 bytes)
```

| Placement (id) | Key struct | Payload struct |
| --- | --- | --- |
| `PartByPartkey` (1) | `{ partkey: i64 }` | `{ p_type: SqlString }` |
| `PartsuppByPartkeySuppkey` (2) | `{ partkey: i64, suppkey: i64 }` | `{ ps_availqty: i32 }` |
| `LineitemByPartkeySuppkeyOrderkeyLinenumber` (3) | `{ partkey: i64, suppkey: i64, orderkey: i64, linenumber: i32 }` | `{ l_shipdate: Date, l_extendedprice: SqlDecimal<15, 2>, l_discount: SqlDecimal<4, 2> }` |

How MI_P differs from COL:

- **No `via`.** Lineitem has its own column in every path domain (`l_partkey`, `l_suppkey`, `l_orderkey`, `l_linenumber`), so a line's key never depends on another table's row. Whether MI_P still needs a side store is an open question in the guide.
- **A node with no placement.** `orderkey` holds nothing; it orders a supply's lines by Lineitem's primary key.
- **Groups are parts.** A group is the first 9 bytes (`prefix_partkey`). One order's lines fall in several groups, one per part.
- **Record order** within a part: the part, then each supply followed by its lines, in supplier order (`record_order_is_the_tries_pre_order`).
- Partsupp's payload, `ps_availqty`, is a placeholder until Q20 or Q2 needs its columns; Q14 does not read Partsupp.

## Tests

```bash
cargo +1.96.1 test --offline --locked     # this directory
```

`src/tests.rs`: golden key and payload bytes, record order, malformed keys, the trie and its constants (`check_against_trie`), prefix widths and ranges, payload validation, and batch consolidation.

`src/storage_tests.rs` sets both storage thresholds to zero, so every run is a file. It keeps what is particular to MI_P; the scale test of DBSP's storage is COL's.

- `file_runs_compact_with_their_prefix_filter_and_preserve_snapshots`: eight interleaved runs of even parts compact in a spine; the compacted file reopens with its rows and its part-group prefix filter (no false negatives; the absent parts, odd ones included, mostly rejected); earlier snapshots keep their rows; after updates that delete a part, change payloads, and move a line to another part, full, prefix, and `RunMerge::seek_group` reads match a `BTreeMap` oracle.
- `seek_group_parks_runs_without_the_part_and_moves_a_line`: a run that lacks the part is parked and counted in `filtered_prefix_probes`; the moved line cancels in its old part and appears in the new one.
- `build_batch_in_follows_the_runtimes_step_placement_in_files` and `_in_memory`.
